# Testing

## Running the tests

```bash
mise run test              # everything
mise run backend:test      # Go
mise run frontend:test     # Vitest, single run
mise run backend:test:cover # Go with a coverage summary
```

Directly, for finer control:

```bash
cd backend
go test ./...                                    # all packages
go test ./internal/domain/                       # one package
go test -run TestCardFlipsWhenThePeriodRollsOver ./internal/occurrence/
go test -v ./internal/api/                       # verbose
go test -count=1 ./...                           # bypass the result cache
go test -race ./internal/occurrence/             # the concurrency test earns this

cd frontend
npm run test                    # single run
npm run test:watch              # watch loop
npx vitest run src/lib/         # one directory
npx vitest run -t "flips"       # by test name
```

## How backend tests are set up

Backend tests run against a **real SQLite database** with the **full migration set
applied**, in a throwaway directory that is deleted afterwards.

```go
app := testutil.NewApp(t)
```

That single line gives you a fully migrated database. `testutil.NewApp` hands
`t.TempDir()` — an empty directory — to `tests.NewTestApp`, which clones it,
bootstraps a fresh database, and runs the system migrations followed by ours.
Cleanup is registered with `t.Cleanup`, so nothing leaks between tests.

This matters more than it sounds. There are **no committed database fixtures**.
PocketBase's own docs suggest creating a `test_pb_data` directory and committing
it, which works but means a binary blob that drifts away from the migrations and
has to be regenerated by hand. Here the tests exercise the same schema, indexes and
API rules that production will have, and a migration that breaks something fails the
tests immediately.

The cost is a couple of seconds per package for migration setup. Worth it.

## Fixtures

`internal/testutil/fixtures.go` builds records directly through `app.Save`, which
bypasses the collection API rules on purpose: tests need to arrange state, and the
rules themselves are covered by the schema and API tests.

```go
func NewUser(t, app, email, name, role string) *core.Record
func NewTeam(t, app, name string, members ...*core.Record) *core.Record
func NewBoard(t, app, team *core.Record, name string) *core.Record
func NewCard(t, app, board *core.Record, title string, cadence domain.Cadence) *core.Record
func Archive(t, app, record *core.Record, by *core.Record)
func CountRecords(t, app, collection string) int
func Collection(t, app, name string) *core.Collection
```

They fail the test on error rather than returning one, so arranging a scenario stays
readable:

```go
app := testutil.NewApp(t)

member := testutil.NewUser(t, app, "member@example.test", "Member", schema.RoleUser)
admin  := testutil.NewUser(t, app, "admin@example.test", "Admin", schema.RoleAdmin)
team   := testutil.NewTeam(t, app, "Platform", member)   // admin is NOT listed
board  := testutil.NewBoard(t, app, team, "Triage")
card   := testutil.NewCard(t, app, board, "Verify Backups", domain.Daily)
```

Note that the admin is deliberately not a member. Admin access comes from the role,
not from membership, and leaving them off the list is what proves it.

`NewCard` mirrors what the production hook does: it sets the denormalised `team`
from the board. If you build cards by hand, set it, or the access rules will not
match.

`CountRecords` is the workhorse for asserting the lazy model:

```go
if n := testutil.CountRecords(t, app, schema.Occurrences); n != 0 {
	t.Errorf("occurrences table holds %d rows, want 0", n)
}
```

## The most common fixture pattern

Most packages define a local `fixture` struct so each test starts from one line.
From `internal/occurrence/occurrence_test.go`:

```go
type fixture struct {
	app    *tests.TestApp
	svc    *occurrence.Service
	member *core.Record
	admin  *core.Record
	autre  *core.Record   // a user on no team at all
	team   *core.Record
	board  *core.Record
	now    time.Time
}

func newFixture(t *testing.T) *fixture { /* ... */ }
```

Having a user who belongs to no team (`autre`) available by default makes it cheap
to check that something is actually denied, which is the assertion people skip.

## Testing time-dependent behaviour

Almost everything in this application depends on what time it is, so the services
take an injectable clock. **Never let a test depend on the real clock** — it will
pass all day and fail at midnight, or fail once a year on a daylight-saving
boundary.

`occurrence.Service` and `rollup.Service` both expose `WithClock`, which returns a
copy:

```go
cal := config.Default().Calendar
frozen := time.Date(2026, 9, 3, 14, 0, 0, 0, cal.Location())

svc := occurrence.NewService(cal).WithClock(func() time.Time { return frozen })
```

Moving through time is then just another clock:

```go
// Complete the card today.
if _, err := svc.Complete(app, card.Id, member, ""); err != nil {
	t.Fatal(err)
}

// Ask again tomorrow, without anything having run in between.
tomorrow := svc.WithClock(func() time.Time { return frozen.AddDate(0, 0, 1) })
state, err := tomorrow.StateOf(app, card)
// state.Status == domain.StatusNotStarted
```

That is the flip, tested. No job ran; the clock moved.

Pick fixed dates with known properties and say so in a comment. `2026-09-03` is a
Thursday in ISO week 36, which is why it appears throughout the tests. Useful dates
for the US Eastern calendar:

| Date | Property |
| --- | --- |
| `2026-09-03` | Thursday, ISO week 36 |
| `2026-09-07` | Monday, starts ISO week 37 |
| `2026-03-08` | Spring forward. This day is 23 hours long |
| `2026-11-01` | Fall back. This day is 25 hours long |
| `2026-01-01` | Thursday, belongs to ISO week `2026-W01`, which starts 2025-12-29 |
| `2027-01-01` | Friday, belongs to `2026-W53` |

`internal/domain/period_test.go` covers all of these. If you touch period
arithmetic, read that file first — it doubles as the specification.

## HTTP and permission tests

`internal/testutil/client.go` drives the **real router** in process: PocketBase's
generated collection endpoints, our custom routes, the API rules and the hooks. It
builds the router exactly as the server does and triggers `OnServe` to collect the
custom routes.

```go
testApp := testutil.NewApp(t)
app.Setup(testApp, config.Default())      // hooks + routes + cron, as in production

client := testutil.NewClient(t, testApp)
token  := testutil.Token(t, member)       // a genuine auth token

res := client.GET(t, "/api/kamishibai/boards/"+board.Id+"/state", token)
if res.Status != http.StatusOK {
	t.Fatalf("status = %d: %s", res.Status, res.Body)
}
```

The methods:

```go
client.GET(t, path, token)
client.POST(t, path, token, body)      // body is marshalled to JSON; nil for none
client.PATCH(t, path, token, body)
client.DELETE(t, path, token)
client.Do(t, method, path, token, body)
```

Pass `""` as the token for an unauthenticated request. Decoding:

```go
var body struct {
	Cards []struct{ Title string } `json:"cards"`
}
res.JSON(t, &body)          // fails the test on malformed JSON
generic := res.Map(t)       // map[string]any when a struct is overkill
```

### Why these tests are not optional

PocketBase access rules are **filter expressions evaluated by the database**. A
mistake in one is not a compile error and not a runtime error. It matches nothing,
and looks exactly like a legitimate denial.

Two real bugs on this project were caught only because these tests assert HTTP
status codes rather than comparing rule strings:

- `team.members ?= X` silently matched nothing, locking members out of their own
  boards. `team.members.id ?= X` is required.
- Create rules are evaluated against the request body before hooks run, so a rule
  referencing a server-derived field rejected every well-formed request.

`schema_test.go` passed throughout both. It compared strings, and the strings were
what the author intended.

**So: if you change an access rule, add a test that makes a request.** Assert both
directions — that the permitted case returns 200 and the forbidden case does not.

```go
// The shape worth copying: prove the allow AND the deny.
func TestBoardCreationIsScopedToOwnTeams(t *testing.T) {
	f := newFixture(t)

	res := f.client.POST(t, "/api/collections/boards/records", f.memberToken,
		map[string]any{schema.FieldTeam: f.team.Id, schema.FieldName: "Mine"})
	if res.Status != http.StatusOK && res.Status != http.StatusCreated {
		t.Fatalf("own team = %d, want success: %s", res.Status, res.Body)
	}

	res = f.client.POST(t, "/api/collections/boards/records", f.memberToken,
		map[string]any{schema.FieldTeam: f.otherTeam.Id, schema.FieldName: "Theirs"})
	if res.Status == http.StatusOK || res.Status == http.StatusCreated {
		t.Errorf("created a board on another team (%d)", res.Status)
	}
}
```

There is also `internal/api/rules_test.go`, which runs rule-shaped filters directly
and asserts how many records they match. It is the fastest way to check that a new
rule resolves at all before wiring it into a migration.

## What the existing suites cover

| Package | Focus |
| --- | --- |
| `internal/domain` | Period arithmetic: keys, boundaries, DST, ISO weeks, ranges. No database, fast |
| `internal/occurrence` | Lazy writes, attribution, idempotency, flipping, archive freezing, authorisation, concurrency |
| `internal/rollup` | Snapshot maths, the "was this card expected then" denominator, backfilling |
| `internal/seed` | Idempotency, determinism across databases, closed-period-only history |
| `internal/api` | HTTP behaviour: auth, tenant isolation, forgery attempts, archive/restore, reporting |
| `migrations` | The schema the migrations produce |

Two worth reading as examples of testing a property rather than a line of code:

**`TestConcurrentWritesProduceExactlyOneRow`** fires eight simultaneous completions
at one card and asserts a single row exists. It tests the unique index and the retry
loop together, which is the only way to test either meaningfully.

**`TestSeedIsIdempotent`** captures the set of `(card title, period, status)`
triples after one run, runs the seeder again, and compares. It caught a real bug: a
single PRNG advanced across the loop consumed a different number of draws when it
created a row, so re-runs invented different history. Comparing row *counts* alone
would have missed it.

## Frontend tests

Vitest with jsdom and Testing Library. Setup is `src/vitest.setup.ts`, which just
imports the jest-dom matchers.

Queries are by **role and accessible name**, not by CSS class:

```tsx
render(<CardTile card={makeCard()} onStart={vi.fn()} /* ... */ />);

expect(screen.getByRole('button', { name: 'Verify Backups' })).toBeInTheDocument();
await userEvent.click(screen.getByRole('button', { name: 'Mark done' }));
```

That is not only about accessibility, though it does mean an accessibility
regression breaks a test. It is also more stable: renaming a class does not break
anything, and a query by accessible name fails loudly if a control stops being
reachable.

Each component test file has a `makeCard()` factory taking overrides, so a test
states only what it cares about:

```tsx
const card = makeCard({}, { status: 'done', completedBy: user('Mei') });
```

### Testing sanitisation

`sanitize.test.ts` is about containment, not formatting. Card instructions are
written by teammates and rendered in everyone else's browser, so the tests assert
that scripts, event handlers, `javascript:` URLs, iframes, forms and style
attributes are all removed, while ordinary prose markup survives.

This suite caught a bug that would have shipped otherwise: DOMPurify drops **all
text** unless `#text` is included in an explicit `ALLOWED_TAGS`. Instructions
rendered as an empty skeleton of tags. The assertion that caught it was the
unglamorous one:

```ts
expect(clean).toContain('Hi');
```

When testing a sanitiser, assert what must survive as well as what must not.

### Ambiguous queries

If a query matches more than one element, Testing Library fails with "Found multiple
elements". Scope it rather than loosening the matcher:

```tsx
// "Check the..." appears in both the instructions and a checklist step.
const instructions = screen.getByRole('region', { name: 'Instructions' });
expect(instructions).toHaveTextContent('Check the backup dashboard.');
```

## Guidelines

**Test the property, not the implementation.** "An untouched card stores nothing"
survives a refactor of the storage layer. "Calls `Find` once" does not.

**Assert the denial.** For anything permission-related, the forbidden case is the
one that matters.

**Freeze the clock.** Any test touching periods should use `WithClock`.

**Check the side effect, not just the return value.** A mutation that returns
successfully while writing two rows is still broken, which is why several tests
finish with a `CountRecords` assertion.

**Say why in a comment when the reason is not obvious.** `2026-03-08 is 23 hours
long` saves the next person a calendar lookup.

## CI

`mise run check` is lint, test and build for both workspaces, and is the quickest way
to find out locally whether CI will be happy.

GitHub Actions runs the same mise tasks on every pull request and every pushed
commit, with `-race` enabled for the Go tests. The Docker build additionally runs
`go vet ./... && go test ./...` inside the image build, so a container that cannot
pass its own tests never gets tagged.

The workflow can be executed on your own machine:

```bash
mise run ci:local                     # the whole workflow, as a pull request
mise run ci:local -- --job backend    # just one job
```

See [CI](ci.md).
